OGO TAG MANAGER 3.11.1

ВИПРАВЛЕННЯ 3.11.1
У 3.11.0 перевірка власника старої адреси могла пройти через фільтр транслітерації WordPress і помилково знайти латинську ціль замість кириличного джерела.
Це блокувало активність 301, появу правила серед неперевірених і видалення вже перенесеного джерела.
Тепер перевіряються фактично збережені slug без фільтрів транслітерації; захист від реального повторного використання адреси зберігається.
Уже виконані перенесення повторювати не потрібно. Після оновлення відкрийте розділ 4, виберіть свою групу Redirection та перевірте правила.
Якщо правила ще не імпортовані, експортуйте потрібні неперевірені рядки у CSV та імпортуйте їх у групу Redirection.
Після перевірки 301 поверніться до розділу 3 → «Підготувати список видалення».
У 3.11.1 пройшли попередні 190 локальних перевірок і 15 нових перевірок цієї помилки; разом 205.

ОНОВЛЕННЯ
Завантажте ogo-tag-manager-v3.11.1.zip через Плагіни → Додати новий → Завантажити плагін та замініть установлену версію.
Рішення, перенесення, зміни slug, правила 301 і пакети CSV попередніх версій зберігаються.
Після оновлення відкрийте Інструменти → OGO Tag Manager. Повторювати вже виконані об’єднання не потрібно.

1. ПАРИ НАЯВНИХ ПОЗНАЧОК
«Знайти пари» показує мовні підказки серед наявних позначок. Нових позначок модуль не створює.
Якщо це різні поняття (політика → політики; Шахтар як клуб → шахтарі), натисніть «Пропустити пару».
Рішення зберігається для конкретної пари в обох напрямках. Позначки та статті залишаються.
Пропущена пара не з’являється після оновлення сторінки, у новому пошуку або як конфлікт у пункті 2.
Для повернення розгорніть «Пропущені пари» → «Показати пропущені пари» → «Повернути до підказок».
Наявне часткове перенесення не можна приховати як пропущену пару — його треба завершити або перевірити.

Виберіть потрібні пари → «Перевірити й об’єднати вибрані» → перегляньте цілі та попередження → підтвердьте.
До статей джерела додається цільова позначка. Наявні зв’язки та джерельна позначка зберігаються до окремого видалення.

ВЕЛИКІ ПЕРЕНЕСЕННЯ
Обмеження «понад 500 зв’язків» для швидкого сценарію прибране.
Великі пари обробляються автоматично невеликими порціями — не більше 100 нових зв’язків за один запит.
Є прогрес, зупинка після поточного запиту та продовження після оновлення сторінки: знайдіть пари й виберіть рядок із позначенням продовження.
Уже додані зв’язки повторно не дублюються. Якщо змінилися джерело, ціль або їхні зв’язки поза операцією, виконання зупиняється для перевірки.
До завершення перенесення редирект не активується, а джерело не пропонується до видалення.
Старі незавершені операції, створені до 3.11.0 без журналу порцій, автоматично не поновлюються — для них залишається розширена панель.

2. КИРИЛИЧНІ SLUG ТА ЇХНІ ДУБЛІКАТИ
«Знайти всі кириличні slug» показує кирилицю, зокрема URL-кодовану.
Якщо запропонований латинський slug вільний, змінюється тільки slug. ID, назва позначки та зв’язки зі статтями зберігаються.
Якщо slug уже належить іншій позначці, показується власник адреси й пропонується об’єднання з ним.
Приклади: кар’єра #8422 → кар'єра #6385; Случ #13161 → СЛУЧ #8811, якщо саме такі позначки й адреси є в базі.
За потреби виправте новий slug або натисніть «Пропустити пару», якщо це різні поняття.
Виберіть рядки → «Застосувати slug та об’єднати дублікати» → перегляньте план кожної дії → підтвердьте.
Конфлікт не перетворюється на автоматичне видалення: модуль переносить статті, перевіряє зв’язки й створює 301, а джерело видаляється окремо в розділі 3.
Два джерела, які ведуть до однієї цілі, можуть оброблятися в одному запуску.
Нормалізація різних апострофів та HTML-сутностей допомагає знаходити наявні адреси на кшталт karyera і polumya.

3. МАСОВЕ ВИДАЛЕННЯ ПЕРЕНЕСЕНИХ ДЖЕРЕЛ
«Підготувати список видалення» повторно перевіряє завершені перенесення й автоматично вибирає всі придатні джерела.
Перегляньте список → «Видалити всі перевірені джерела…» → підтвердьте кількість.
Самі статті, цільові позначки, журнали та правила 301 залишаються. Видаляється стара позначка та її власні зв’язки й метадані.
Джерела з описом, власними SEO-налаштуваннями, зміненими статтями або непідтвердженим перенесенням пропускаються з причиною.
Видалення позначок незворотне; відкат перенесення після нього недоступний. Частковий запуск можна продовжити повторною підготовкою списку.

4. НЕПЕРЕВІРЕНІ РЕДИРЕКТИ ТА REDIRECTION
Замість повного списку активних правил головна сторінка показує тільки неперевірені редиректи.
Після оновлення спочатку виберіть свою окрему групу Redirection → «Зберегти групу» → «Перевірити редиректи».
Це прибере зі списку старі правила, які вже були імпортовані та працюють. Не імпортуйте повний старий реєстр повторно.
Для решти натисніть «Експортувати неперевірені в CSV», імпортуйте файл у вибрану групу Redirection та знову натисніть «Перевірити редиректи».
За наявності вибраних рядків перевіряються вони; без вибору — всі неперевірені. Є окрема зупинка після поточної HTTP-перевірки.

Перевірка зараховується тільки якщо:
— у вибраній активній групі Redirection є відповідне увімкнене звичайне URL-правило з кодом 301;
— старий URL повертає прямий 301 на потрібну адресу без ланцюжка;
— відповідь підтверджує Redirection як джерело перенаправлення;
— кінцевий URL повертає HTTP 200.

Тільки після цього рядок ховається зі списку й наступного CSV. Саме завантаження файлу не позначає його як імпортований.
Якщо перевірка не пройшла, правило залишається з причиною: його немає у групі, ціль неправильна, HTTP-помилка, кеш тощо.
Серверні запити виконуються лише до власного сайту. Хостинг, захист чи проксі можуть їх блокувати або прибирати службові заголовки; такий результат не вважається успіхом.
Підтримуються прямі URL-правила. Regex і умовні перенаправлення не позначаються автоматично перевіреними.
Модуль не створює, не імпортує й не видаляє правила або групи в Redirection. Імпорт CSV виконує користувач.

ТИМЧАСОВА ПІДСТРАХОВКА 301
До перевірки старі адреси продовжує обслуговувати OGO Tag Manager, поки плагін активний.
Під час HTTP-перевірки підписаний службовий заголовок вимикає саме цю підстраховку для конкретного запиту, щоб власний 301 не зарахувався як Redirection.
Після успіху звичайні запити передаються зовнішньому правилу Redirection. Якщо воно вимкнене, видалене або ціль змінилася, OGO відновлює підстраховку, а рядок повертається до неперевірених.
Повна резервна копія правил і журнали пакетів CSV залишаються у згорнутому розділі нижче. Звичайні пакетні CSV теж не включають уже перевірені правила.
Формат CSV: source,target,0,301; без заголовка і BOM. Повторний імпорт того самого завантаженого файлу контролюйте в Redirection.
Власні правила OGO працюють для точних адрес архівів позначок, GET і HEAD; пагінація, фіди та довільні query-параметри окремо не мігруються.
