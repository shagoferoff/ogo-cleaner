# Очищення рекламних посилань за CSV (6)

Редакція уточнила: список статей уже погоджений і зовнішні посилання в них є
рекламними. Повторне погодження доменів або окремий інвентаризаційний звіт
не потрібні. Область — тільки основний `post_content`; `anons` не змінюється.

Джерело — 2 207 унікальних опублікованих записів із CSV користувача.
Вони входять у погоджені 2 215 ID з видимих аркушів. 8 ID не потрапили
в експорт і не отримують правок. У 1 923 статтях є 1 925 зовнішніх HTTP(S)
посилань. 284 статті без таких посилань залишаються без змін.

Прибираються тільки відкривальні/закривальні теги a зовнішніх вебпосилань.
Весь текст анкора, вкладене форматування, медіа, решта HTML, пробіли та
переноси залишаються побайтово такими самими. Окремі абзаци не видаляються.
Адреси ogo.ua/ogo.rv.ua з піддоменами, відносні посилання, mailto/tel,
коментарі, блоки коду та скрипти зберігаються. Пробіли в шляху зовнішнього
URL не заважають зняттю тега, якщо домен визначається однозначно.

## Застосування

1. Зробити актуальну резервну копію бази.
2. У phpMyAdmin бази `ogo2023_ogo` імпортувати
   [ogo-miralinks-clean.sql.gz](../dist/ogo-miralinks-clean.sql.gz) без розпакування.
   Це gzip-копія [звичайного SQL](../dist/ogo-miralinks-clean.sql),
   менша за типовий ліміт завантаження 2 МБ.
3. Наприкінці запит покаже planned_articles, backed_up, skipped_before_backup,
   cleaned, original і changed_since_backup. Очікувано planned_articles=1923;
   cleaned=1923, якщо від експорту не було змін. Менша кількість означає
   пропущені записи; не примушуйте їх до запису видаленням перевірок.
4. Очистити кеш WordPress, об'єктний кеш (зокрема Redis), кеш сторінок/CDN,
   якщо вони використовуються. Перевірити кілька матеріалів на сайті.

У разі потреби імпортувати
[ogo-miralinks-restore.sql](../dist/ogo-miralinks-restore.sql).
Цей файл відновлює тільки записи, які все ще точно відповідають результату
очищення; подальші зміни тексту, статусу чи дати публікації не перезаписує.
Після відкату також очистити кеш. Резервна таблиця не видаляється.

SQL не потребує плагіна або JavaScript. Не відключайте антивірус для його
використання. Файли призначені саме для цієї бази, префікса wp_ та цього CSV,
а не для інших сайтів чи довільних статей.

## Захист і обмеження

Перед змінами створюється окрема таблиця
`wp_ogo_miralinks_backup_de0a5dfdeb16` зі справжнім поточним текстом і
контрольними сумами. Вона заповнюється тільки для записів, які відповідають
CSV за ID, типом post, статусом publish, датою публікації та SHA-256 тексту.
Резервні рядки фіксуються через COMMIT до початку першого UPDATE статті.
Повторний запуск дозволений, резервні оригінали не перезаписуються.

Кожен UPDATE додатково звіряє збережений оригінал, поточний текст і SHA-256
обчисленого результату. Редакторська зміна між резервуванням і UPDATE
призводить до пропуску. Правки задаються байтовими позиціями тегів, застосованими
справа наліво через INSERT(BINARY ...). Глобального REPLACE немає: однаковий
текст посилання всередині коментаря або коду не зачіпається.

SQL змінює лише post_content. Заголовки, статуси, дати публікації/модифікації
й postmeta не змінюються. Це прямий запит до БД: хуки WordPress, ревізії та
скидання кешу не викликаються. Відновлення забезпечує окрема резервна таблиця;
очищення кешу виконується вручну після імпорту.

У публічних SQL-файлах є лише ID, контрольні суми й позиції тегів. Повні
тексти, вихідний CSV, Excel і локальний план не публікуються.
Генератор — `scripts/build-miralinks-sql.php`, парсер — `scripts/miralinks-unwrap.php`.

## Перевірки

`tests/miralinks-unwrap.php`: точне збереження UTF-8/emoji, форматування, HTML,
CRLF, внутрішніх адрес, коментарів/коду, повторний запуск, пошкоджені anchors.

`tests/miralinks-sql.py`: окрема тимчасова БД MariaDB, усі 2 207 наданих текстів,
1 923 реальних UPDATE, точні хеші результатів, фіксація резервів до змін,
незмінність дат/заголовків/postmeta, повторний запуск, відкат зі збереженням
подальших правок, пропуск застарілого CSV та зміненого статусу. Тестова БД
видаляється після перевірок; робоча база не використовується.
